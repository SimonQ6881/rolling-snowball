# README 与仓库说明文档设计

## 1. 背景

当前仓库已经完成首次远端上传，具备代码、配置、数据、报告和文档等完整内容，但根目录 `README.md` 仍偏向“当前开发者自己使用”的记录式说明。

对于首次进入仓库的开发者来说，现有说明还存在几个问题：

- 能快速跑起来，但不够快地理解“这个项目到底是什么”
- 能看到若干目录和脚本，但不容易判断“哪些是当前主线，哪些是历史遗留”
- 能找到一些文档，但缺少清晰的阅读顺序和导航关系
- 对数据来源、运行依赖、开发入口、协作边界的说明还不够系统

本次目标不是重做全部项目文档，而是先把仓库级入口整理好，让一个新接手的开发者能在较短时间内完成“理解项目定位 -> 跑起本地环境 -> 找到主线代码 -> 找到更详细文档”的完整路径。

## 2. 目标

本次文档改造的目标是：

- 重写根目录 `README.md`，让它成为 GitHub 仓库首页和开发入口
- 新增 `docs/repository-guide.md`，承接更完整的开发者向仓库说明
- 明确当前主线与历史模块边界，减少误读和误改
- 建立文档导航关系，让 README、状态文档、规格文档、历史说明形成清晰分工

本次不包含：

- 全量清理历史文档
- 重写每个模块的独立技术文档
- 对外营销式包装或开源宣传文案

## 3. 目标读者

优先服务对象是后续继续开发或接手维护本仓库的开发者。

次级服务对象包括：

- 需要快速了解产品主线的产品协作者
- 需要浏览仓库结构和入口的审阅者

因此文档表达优先级为：

1. 项目定位清楚
2. 本地启动顺畅
3. 主线代码与文档入口明确
4. 历史遗留边界可辨认

## 4. 文档方案

采用“平衡双文档”方案：

- `README.md`
  - 作为仓库首页入口
  - 负责介绍项目定位、核心能力、快速开始、主线结构和文档导航
- `docs/repository-guide.md`
  - 作为更完整的仓库说明文档
  - 负责介绍系统组成、目录职责、数据与依赖、开发路径、协作约定和相关文档索引

这种方案的原因是：

- 只扩写 `README.md` 会让首页过长，影响首屏可读性
- 只保留精简 README 又会让首次接手者跳转过多，无法快速建立整体认知
- 双文档方案能兼顾 GitHub 首页阅读体验和后续持续维护

## 5. README 设计

### 5.1 角色定位

`README.md` 应承担以下职责：

- 一句话讲清项目是什么
- 明确当前主线闭环和典型使用场景
- 让开发者能按步骤完成本地启动
- 给出仓库结构总览和关键脚本入口
- 引导读者继续阅读更详细的文档

### 5.2 建议结构

建议包含以下章节：

1. 项目概述
2. 当前主线能力
3. 技术栈与系统组成
4. 快速开始
5. 常用命令
6. 目录结构
7. 主线页面与路由
8. 文档导航
9. 历史模块说明

### 5.3 内容风格

- 语言保持直接、克制、开发者友好
- 避免过长的背景铺垫，优先给出结论
- 每一段都围绕“下一步该做什么”组织
- 用列表和代码块承接高频操作，减少大段叙述

## 6. 仓库说明文档设计

### 6.1 角色定位

`docs/repository-guide.md` 用于承接 README 不适合展开的内容，重点帮助开发者理解仓库内部的结构与约定。

### 6.2 建议结构

建议包含以下章节：

1. 仓库全景
2. 当前主线与历史模块边界
3. 系统组成
4. 数据与依赖
5. 常用开发路径
6. 常用命令与脚本职责
7. 文档索引
8. 协作约定

### 6.3 关键说明点

应重点写清：

- `frontend-console/`、`src/rolling_snowball/`、`scripts/`、`sql/`、`data/` 的职责
- PostgreSQL、Tushare、本地数据文件在项目中的角色
- 当前主线优先阅读哪些文件
- 看到哪些命名应按“历史模块”理解
- 哪些内容已被忽略，不应该提交到仓库

## 7. 具体落地范围

本次实施时需要完成：

- 改写根目录 `README.md`
- 新增 `docs/repository-guide.md`
- 在 `README.md` 中加入到仓库说明文档和现有状态文档的链接
- 保持与现有 `docs/current-console-status.md`、`docs/legacy-modules.md`、`scripts/README.md` 的内容口径一致

本次实施时不修改：

- 当前控制台功能实现
- 数据表结构
- 脚本行为
- 历史模块代码

## 8. 风险与约束

### 8.1 风险

- 如果 README 写得过细，后续容易与状态文档重复维护
- 如果仓库说明写得过抽象，无法真正降低接手成本
- 如果主线与历史模块边界写得不清楚，仍可能误导后续开发

### 8.2 约束

- 必须与仓库当前真实结构一致，不能写出不存在的能力
- 必须承认历史模块仍存在，而不是假装仓库只有当前主线
- 必须保留本地单用户研究工具这一定位，不扩写成未实现的平台化叙事

## 9. 验收标准

完成后，这两份文档应满足以下标准：

- 新读者打开 `README.md` 后，能在 1 到 3 分钟内理解项目定位和主线范围
- 新开发者能按文档说明完成环境准备和本地启动
- 阅读 README 后，能明确继续看哪些文档、哪些目录、哪些脚本
- 看到历史模块时，能知道它们不是当前主线
- 仓库说明文档能作为后续继续开发的稳定导航页

## 10. 实施顺序

建议按以下顺序执行：

1. 重写 `README.md` 结构
2. 新增 `docs/repository-guide.md`
3. 统一文档间链接和导航关系
4. 自检是否存在重复、矛盾、过时描述
