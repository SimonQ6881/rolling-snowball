# Rolling Snowball 前端控制台设计

## 1. 背景

当前项目已经具备以下基础能力：

- PostgreSQL 本地数据库与评分表结构
- 股票主档同步
- 评分流水线执行
- 全市场与小样本评分运行
- `重点观察池 / 观察池` 结果产出

但当前使用方式仍然偏脚本化，主要依赖命令行运行和数据库查询。随着规则迭代、参数实验和结果复核频率提升，仅靠命令行和 SQL 已不够高效。

用户需要一个本地前端控制台，满足两类核心需求：

1. 更方便地查询和比较结果
2. 能在前端调整规则参数、发起筛选任务、查看进度和日志

本设计聚焦第一版控制台，优先保证“结果查询闭环”，同时提供够用的任务运行和规则实验能力。

## 2. 目标

第一版控制台目标如下：

- 首页默认展示 `重点观察池`
- 支持跳转到 `全股票列表` 与 `行业看板`
- 支持进入单股 `独立详情页`
- 详情页默认提供 `同行业对比`
- 提供 `规则实验台`，允许编辑：
  - 硬过滤阈值
  - 评分权重
- 支持两种参数生效方式：
  - 仅本次运行生效
  - 保存为默认规则
- 提供 `任务运行页`，展示：
  - 运行状态
  - 基础进度
  - 实时日志流
- 每次运行都可按 `run_id` 独立查看结果，避免不同实验结果相互覆盖

## 3. 非目标

第一版明确不做以下内容：

- 多用户与权限系统
- 登录认证
- 回测系统
- 拖拽式规则编排器
- 复杂图表大屏
- 人工分析报告编辑器
- WebSocket 实时推送
- 复杂规则模板市场

第一版优先使用本地单用户、轮询式交互、清晰可维护的结构。

## 4. 总体方案

采用 `查询主站 + 规则实验台` 结构。

### 4.1 一级模块

- `重点观察池首页`
- `全股票列表`
- `行业看板`
- `股票详情页`
- `规则实验台`
- `任务运行页`

### 4.2 架构分层

控制台采用三层结构：

1. 前端 Web 控制台
2. 本地 Python 后端服务
3. 评分任务执行层

#### 前端 Web 控制台

负责：

- 页面展示
- 条件筛选
- 排序分页
- 参数编辑
- 任务状态轮询
- 日志展示

不直接连数据库，只调用本地 API。

#### 本地 Python 后端服务

负责：

- 结果查询接口
- 详情与行业对比接口
- 规则读取与校验
- 启动评分任务
- 返回任务状态与日志

实现风格建议复用项目现有本地 HTTP 服务模式，不强依赖重框架。

#### 评分任务执行层

复用现有评分能力：

- `scoring_pipeline.py`
- `run_scoring_bootstrap.py`

但新增一层任务管理器，负责：

- 创建 `task_id`
- 创建 `run_id`
- 记录运行参数快照
- 启动后台任务
- 持续写入进度与日志
- 结束后更新任务状态和结果链接

## 5. 页面设计

## 5.1 重点观察池首页

作为默认首页。

### 页面内容

- 最近一次成功运行摘要：
  - 运行时间
  - `run_id`
  - 规则版本
  - 重点观察池数量
  - 观察池数量
- 重点观察池主表格：
  - 股票代码
  - 股票名称
  - 申万一级行业
  - 总分
  - 行业排名
  - warning 标签
- 顶部快捷入口：
  - 查看全股票列表
  - 查看行业看板
  - 发起新运行

### 默认数据口径

- 默认加载最近一次成功运行的 `重点观察池`
- 页面始终显示当前查看的 `run_id`

## 5.2 全股票列表

用于全量结果查询。

### 功能

- 展示当前 `run_id` 下全部股票结果
- 支持筛选：
  - 池子
  - 行业
  - 分数区间
  - 是否被过滤
  - warning 标签
- 支持排序：
  - 总分
  - 行业排名
  - 股票名称
  - 股票代码
- 支持分页

## 5.3 行业看板

用于从行业视角查看结果。

### 展示指标

- 行业股票数
- 行业平均分
- 行业最高分
- 行业内重点观察池数量
- 行业内观察池数量

### 交互

- 点击某行业后进入该行业股票列表
- 可切回重点观察池或全股票列表

## 5.4 股票详情页

点击任意股票后进入独立详情页。

### 信息分区

1. 基本信息区
   - 股票代码
   - 名称
   - 行业
   - 当前池子
   - 总分
   - 行业排名 / 行业总数
   - 全市场排名

2. 一级维度区
   - 业务质量
   - 成长兑现度
   - 财务质量
   - 估值匹配度

3. 二级指标区
   - 原始值
   - 分项得分
   - 加权后分数

4. 运行与规则信息区
   - `run_id`
   - `rule_version`
   - `data_version`
   - `latest_report_period`
   - `audit_opinion`
   - `warning_tags`
   - `filter_reasons`

## 5.5 详情页内同行业对比

第一版对比方式固定为“默认同行业对比”。

### 展示内容

- 当前股票所在行业内高分股票
- 当前股票行业排名
- 当前股票与同行对比：
  - 总分
  - 四个一级维度
  - 行业排名

### 第一版范围

- 默认展示同行业前若干名高分股票
- 不做自定义任意勾选对比

## 5.6 规则实验台

用于参数实验与规则沉淀。

### 第一版开放编辑项

1. 硬过滤阈值
   - 市值门槛
   - 成交额门槛
   - 资产负债率阈值
   - 现金转化率阈值
   - 其他首版已配置硬过滤阈值

2. 评分权重
   - 一级维度权重
   - 二级指标权重

### 生效方式

用户每次提交时可选择：

- `仅本次运行生效`
- `保存为默认规则`

### 第一版交互要求

- 前端提交前做基础校验
- 后端再次做强校验
- 权重必须满足总和约束
- 数值型阈值必须满足上下限约束

## 5.7 任务运行页

用于执行任务和查看过程。

### 展示内容

- `task_id`
- `run_id`
- 当前状态
- 开始时间
- 已处理数量
- 成功数量
- 失败数量
- 完成时间
- 实时日志流

### 交互

- 运行中定时轮询状态和日志
- 运行完成后展示“查看结果”按钮
- 点击后跳转到对应 `run_id` 的结果首页

## 6. 数据流设计

第一版以 `run_id` 作为结果查看主轴。

### 核心原则

- 所有查询都基于某次运行结果
- 前端明确知道当前查看的是哪个 `run_id`
- 新运行完成后进入新的 `run_id`
- 历史运行可回看，不与最新结果混淆

### 页面数据流

1. 首页加载最近一次成功运行摘要
2. 首页加载该 `run_id` 的重点观察池结果
3. 全股票列表和行业看板复用同一 `run_id`
4. 点击股票进入该 `run_id + ts_code` 的详情页
5. 详情页自动请求同行业对比数据
6. 规则实验台提交参数后创建新任务
7. 任务运行页轮询 `task_id`
8. 任务完成后拿到对应 `run_id`
9. 前端跳转到新 `run_id` 的结果首页

## 7. 数据存储调整

当前 `stock_latest_scores` 只适合保存最新快照，不适合前端按 `run_id` 回看历史结果。

### 现状问题

- 当前结果表是一股一行
- 后跑会覆盖先跑
- 前端无法稳定回看不同实验结果

### 建议调整

保留 `stock_latest_scores` 作为“最新快照表”，同时新增历史结果表。

建议新增：

- `stock_run_scores`

建议主键：

- `(run_id, ts_code)`

### 用途分工

- `stock_latest_scores`
  - 查询最新结果
  - 首页快速加载
- `stock_run_scores`
  - 按运行查看历史结果
  - 参数实验回看
  - 后续支持跨 run 对比

## 8. API 设计

## 8.1 结果查询 API

- `GET /api/runs/latest`
- `GET /api/runs`
- `GET /api/runs/{run_id}/summary`
- `GET /api/runs/{run_id}/stocks`
- `GET /api/runs/{run_id}/industries`
- `GET /api/runs/{run_id}/stocks/{ts_code}`

### 用途

- 首页
- 全股票列表
- 行业看板
- 股票详情页

## 8.2 对比 API

- `GET /api/runs/{run_id}/stocks/{ts_code}/peers`

### 用途

- 详情页默认同行业对比

## 8.3 规则实验台 API

- `GET /api/rules/active`
- `POST /api/rules/validate`
- `POST /api/runs`

### `POST /api/runs` 请求内容

- 规则快照
- 生效方式：
  - `run_once`
  - `save_as_default`
- 可选运行范围

## 8.4 任务进度 API

- `GET /api/tasks/{task_id}`
- `GET /api/tasks/{task_id}/logs`

### 用途

- 任务运行页轮询状态
- 日志流展示

## 9. 任务管理设计

建议区分 `task_id` 与 `run_id`。

### 定义

- `task_id`
  - 表示一次前端触发的后台执行任务
  - 负责展示运行过程
- `run_id`
  - 表示一次评分结果归档
  - 负责结果查询与历史留存

### 执行流程

1. 前端提交运行请求
2. 后端生成 `task_id`
3. 后端创建对应 `run_id`
4. 后台线程或子进程启动评分流程
5. 持续写入任务状态与日志
6. 结束后更新任务状态
7. 将 `run_id` 返回给前端
8. 前端跳转到结果页

## 10. 错误处理

第一版重点处理以下错误：

1. 任务启动失败
   - 数据库连接失败
   - 参数非法
   - 外部数据源配置异常

2. 任务执行失败
   - 评分流程异常中断
   - 日志中断

3. 参数不合法
   - 权重和不正确
   - 阈值越界
   - 区间关系错误

4. 空结果
   - 无数据
   - 筛选为空
   - 运行未完成

5. 历史字段缺失
   - 老 run 缺少部分新字段时，前端用 `--` 展示，不阻断页面

## 13. 实施建议顺序

建议按以下顺序推进实现：

1. 后端历史结果存储与任务表结构
2. 查询 API
3. 首页 / 全列表 / 行业看板
4. 股票详情页与同行业对比
5. 规则实验台
6. 任务运行页
7. 联调与端到端验证

## 14. 风险与取舍

### 风险 1：历史结果结构不足

如果不新增按 `run_id` 存储的结果表，前端会很难稳定支撑“参数实验后回看结果”。

### 风险 2：规则编辑范围过大

第一版只开放硬过滤阈值与评分权重，避免规则编辑器膨胀。

### 风险 3：实时进度实现复杂度

第一版采用轮询，不做 WebSocket，以更低成本获得稳定体验。

### 风险 4：旧数据兼容性

前端需要容忍历史 run 字段不完整，避免一次 schema 演进影响回看体验。

## 15. 结论

第一版控制台将采用“查询主站 + 规则实验台”结构：

- 用结果查询作为主入口
- 用 `run_id` 作为结果主视角
- 用独立任务页承接运行过程
- 用轻量本地服务承接 API 和任务管理

这套方案可以在不过度扩张复杂度的前提下，把当前脚本式工作流升级为一个可持续迭代的本地选股工作台。
