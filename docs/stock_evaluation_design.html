项目核心概述

本项目旨在将现有“自动选股工具”重构为“股票评估工具”，系统核心定位从“全市场自动遍历 + 自动输出股票名单”切换为“宏观与行业方向指引 + 用户自主提交股票 + 系统标准化量化评估 + 结果历史沉淀与多维对比”。

核心定位：系统不再替用户做全市场自动选股，而是帮助用户在既定宏观与行业框架下，对指定股票进行标准化、可解释、可追溯的评估。

业务目标

  • 建立“宏观-行业-个股”一体化评估闭环
  • 支持用户自主录入 A 股、港股股票代码
  • 输出标准化个股评估报告与历史对比结果
  • 实现全量评估结果结构化存储与版本追溯

设计边界

  • 不再执行全市场自动遍历选股
  • 不包含自动交易与下单能力
  • 不以高频择时为目标
  • 优先服务研究驱动、低频决策场景

设计初衷

项目开发背景

现有工具以“全市场自动遍历 + 自动选股”为核心，这类模式更适合广撒网式的量化筛选，不适合研究驱动、低频决策、强调可解释性的投资分析场景。随着使用目标逐步聚焦于“先判断宏观与行业方向，再对具体标的做深入评估”，原有工具在产品定位、数据结构、交互方式和结果输出形态上均已不再匹配新的业务需求。

因此，本项目将原系统重构为“股票评估工具”，系统不再承担自动生成候选股票池的职责，而是转为面向用户已关注标的的标准化评估平台，围绕“宏观-行业指引 + 个股量化评估 + 历史对比分析”形成完整闭环。

解决的核心痛点

  1. 原工具以自动遍历全市场为核心，输出结果噪声高，难以承接研究驱动型投资流程。
  2. 缺乏“宏观方向判断 -> 行业赛道筛选 -> 个股评估”的前置引导能力，用户仍需在系统外完成大量判断。
  3. 个股评估结果缺乏统一规则、版本记录和历史追踪，不利于长期研究积累。
  4. 缺乏跨股票横向对比和同一股票跨时间纵向对比能力，难以支持多标的决策。
  5. 数据结构与导出能力不足，无法直接为 AI 编程、自动化分析和二次开发提供稳定输入。

业务目标与技术目标

业务目标

  • 将系统定位从“自动选股工具”升级为“投资评估工作台”。
  • 为用户提供清晰的宏观与行业赛道指引，帮助用户先确定研究方向，再提交具体股票代码。
  • 为用户提交的 A 股、港股股票生成标准化、可解释、可追溯的量化评估报告。
  • 将所有评估结果结构化入库，支持历史沉淀、横向对比、纵向趋势分析和导出。
  • 为后续 AI 工具调用、规则调整、市场扩展提供标准化接口和数据基础。

技术目标

  • 建立分层清晰、配置驱动的系统架构，避免评分逻辑写死在代码中。
  • 支持宏观指引、行业指引、个股评估、结果存储、对比分析的模块化解耦。
  • 支持规则版本管理，保证历史评估结果可追溯。
  • 支持异步任务机制，满足批量评估、导出和定时刷新等场景。
  • 支持后续新增美股等市场，仅通过扩展适配层而非重写核心引擎完成升级。

需求来源与优先级排序

需求来源说明

  • 业务侧需求：从“自动选股”转向“用户自主选股后标准化评估”。
  • 分析侧需求：强化宏观与行业赛道指引能力，使系统在个股评估前即提供方向性建议。
  • 工程侧需求：要求输出结构化、标准化、可供 AI 直接解析和生成代码的技术文档。

需求优先级排序

优先级 范围 说明
P0 宏观及行业赛道指引、股票代码录入与校验、个股标准化量化评估、评估结果入库与版本管理、单股评估报告展示 必须首批交付，构成主链路闭环
P1 同行业横向对比、同股历史纵向对比、Excel/PDF 导出、手动刷新指引、任务进度与状态通知 应在首个完整版本交付
P2 规则配置后台、数据备份管理页面、维度钻取分析、多市场扩展能力 后续增强能力

设计思路

整体设计原则

  • 从“系统替用户选股”转变为“系统帮助用户评估股票”。
  • 先做方向指引，再做个股评估，符合真实研究流程。
  • 以标准化评分为主，以解释性输出为辅，兼顾量化与可读性。
  • 以配置驱动规则，以版本管理保障可追溯性。
  • 以异步任务支撑长耗时计算，以结构化存储支撑历史分析与 AI 调用。

架构选型推演

方案一：单体式同步应用

该方案将页面、接口、评分逻辑、数据拉取、导出全部放入单一后端服务，同步执行。

优点

  • 开发快，初始实现简单
  • 模块少，部署门槛低

缺点

  • 长耗时操作会显著拉高接口响应时间
  • 后续扩展新市场、新规则时耦合度过高
  • 无法优雅支持批量评估、任务进度和异步重试

结论：不适合作为中长期方案。

方案二：前后端分离 + 异步任务 + 配置化规则引擎

该方案采用前后端分离架构，后端负责接口、评分引擎、任务编排、数据存储，长耗时任务异步处理，评分规则通过配置文件与版本表管理。

优点

  • 更适合批量评估、导出、定时刷新场景
  • 模块边界清晰，便于后续扩展
  • 规则可以配置化和版本化，便于维护
  • 更适合与 AI 编程工具、自动化系统集成

缺点

  • 初期设计成本更高
  • 需要额外引入 Redis、任务队列等中间件

结论：作为本项目推荐架构。

最终架构选型

本系统采用“前后端分离 + 异步任务 + 配置化评分引擎 + 结构化存储”的架构模式，整体分为展示层、接口层、业务层、任务层和数据层五层。

核心技术栈选型理由

层级 技术栈 选型理由
前端 React + TypeScript + Ant Design + ECharts 适合复杂工作台页面、强组件化、图表能力好
后端 FastAPI + Pydantic + SQLAlchemy 结构化 API 能力强，适合定义清晰的数据模型与接口契约
异步任务 Celery + Redis 适配批量评估、导出、月度刷新、失败重试
数据库 PostgreSQL 适合结构化业务数据、历史追溯、JSONB 规则配置
文件存储 MinIO 适合存储导出文件、快照文件、备份文件

与同类方案的差异化对比

维度 传统自动选股工具 本项目股票评估工具
核心定位 从全市场自动筛选股票 对用户指定股票做标准化评估
用户角色 被动接收系统推荐 主动提交标的，系统辅助判断

程序设计方案

模块拆分方案

宏观及行业赛道指引模块

  • 聚合宏观与行业数据
  • 按权重计算宏观分、行业分、细分赛道分
  • 输出图表数据、解读文本和 Top5 赛道结果
  • 维护每月指引版本

用户自主选股交互模块

  • 接收用户输入的股票代码
  • 执行格式校验、上市状态校验、市场与板块识别
  • 控制单次最多 10 只股票的提交限制
  • 创建评估任务并跟踪进度

个股量化评估模块

  • 拉取个股行情、财务、经营、行业基准数据
  • 执行 5 个一级维度、15 个二级指标评分
  • 生成综合得分、扣分点、建议文本
  • 绑定当前宏观/行业版本与评分规则版本

评估结果存储模块

  • 保存评估主结果、维度得分、原始指标、排名结果
  • 实现同股多次评估历史留存
  • 管理导出记录、规则版本、备份日志

多维度历史对比模块

  • 自动生成同行业已评估股票横向对比
  • 生成同股多期纵向趋势
  • 支持最多 5 只股票主动对比
  • 支持维度钻取到底层数据和差异成因

关键功能实现逻辑

评分引擎核心逻辑

评分引擎以 5 个一级维度、15 个二级指标为核心：

  1. 估值维度：市盈率、市净率、市销率
  2. 盈利维度：ROE、毛利率、净利率
  3. 成长维度：营收增速、净利润增速、研发投入增速
  4. 财务健康维度：资产负债率、流动比率、经营现金流净额/净利润
  5. 竞争力维度：市场份额、毛利率偏离行业均值、研发投入占营收比
拉取原始指标值
-> 获取行业均值 / 行业TOP30均值 / 历史分位数 / 安全阈值
-> 对每个二级指标进行标准化评分
-> 聚合得到一级维度得分
-> 按一级维度权重聚合综合得分
-> 生成评级、扣分点和建议

股票代码校验

  • 判断输入长度与格式
  • A 股使用 6 位数字规则，并根据前缀识别沪市、深市、创业板、科创板
  • 港股使用 5 位数字规则，并通过主数据表判断是否为主板或 GEM
  • 对格式正确但不存在或非上市主体的代码返回明确错误原因

批量评估任务

  • 用户提交代码列表后创建评估任务主记录
  • 为每只股票创建任务明细记录
  • 由 Celery Worker 并发执行单股评估
  • 每只股票完成后更新任务进度
  • 任务结束后返回整体状态为成功、部分成功或失败

同行业对比

  • 读取当前股票所属二级赛道
  • 获取数据库中同赛道已评估股票的最新结果
  • 计算综合分排名、分位值、各维度高低差异
  • 输出优势维度、短板维度和雷达图数据

异常处理原则

  • 所有可预期异常必须返回结构化错误码与错误信息
  • 外部数据源异常优先降级，无法降级时标记任务失败
  • 单只股票评估失败不应导致整批任务整体失败
  • 所有异常必须记录日志，支持后续追踪

异常降级策略

  • 若宏观指引刷新失败，保留上一版本并提示“当前展示为最近成功版本”
  • 若某只股票缺失部分财务数据，可按规则降级为“缺失项不计分并提示风险”
  • 若导出失败，保留业务结果并允许用户重试

性能优化策略

评估性能优化

  • 行业均值、行业 TOP30 均值、历史分位数预计算并缓存
  • 批量任务采用异步并发处理
  • 单只股票评估过程严格限制同步阻塞操作
  • 外部数据请求采用连接池与超时控制

查询性能优化

  • 对股票代码、评估时间、版本号、行业字段建立索引
  • 历史评估主表按月份或季度分区
  • 热点报告和指引摘要使用 Redis 缓存
  • 对横向对比结果可做预计算并入库

前端性能优化

  • 大表分页加载
  • 图表按需渲染
  • 首屏只加载摘要数据，详情异步拉取
  • 导出、对比、趋势等重数据操作使用独立请求

可维护性与扩展性设计

配置化策略

以下内容必须配置化：

  1. 一级维度权重
  2. 二级指标权重
  3. 评分阈值
  4. 建议文案模板
  5. 行业映射规则
  6. 指引评分规则

日志与监控

系统需至少记录以下日志：

  • 指引刷新日志
  • 股票校验日志
  • 评估任务日志
  • 导出任务日志
  • 规则发布日志
  • 备份任务日志

监控指标建议包括：

  • 单股评估耗时
  • 批量任务成功率
  • 接口平均响应时间
  • 数据源失败率
  • 导出成功率
  • 数据库查询耗时

关键非功能实现说明

  • 单只股票评估响应时长不超过 30 秒：通过预聚合、异步拉数、并发执行实现
  • 10 只股票批量评估不超过 5 分钟：通过 Worker 并发和任务拆分实现
  • 数据库查询响应不超过 2 秒：通过索引、缓存和查询优化实现
  • 支持 50 名用户同时在线：通过前后端分离、缓存和多实例部署实现

扩展性落地方式

  • 市场适配单独抽象为适配层
  • 评分引擎只消费标准化后的统一指标模型
  • 新增美股时只需增加代码校验器、主数据映射、数据连接器和市场口径适配器

第一阶段 完成主数据、代码校验、任务系统、评估主链路、宏观指引摘要和单股评估报告页
第二阶段 完成横向对比与纵向趋势、规则配置后台、更丰富的图表与钻取
第三阶段 完成多市场扩展、更细粒度权限控制、AI 自动化工作流集成

总结

本项目的核心不是“找股票”，而是“评估股票”。其设计初衷是将投资研究流程产品化、标准化、结构化，使系统从“自动筛选器”升级为“研究型评估平台”。

从设计思路上，系统围绕“方向指引、个股判断、历史对比、结果沉淀”四个关键环节展开，并采用前后端分离、异步任务、规则配置化、结果版本化的技术路线，以保证系统具备可扩展、可维护、可解释的长期能力。

从程序设计方案上，系统通过模块解耦、统一接口、结构化存储、规则版本管理、异常降级和性能优化等手段，确保既能满足当前 A 股与港股评估需求，也能为后续 AI 编程、规则迭代和多市场扩展打下稳定基础。
